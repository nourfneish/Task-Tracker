# Reflection

I used Claude throughout this module in three roles: as a code reader (to understand the existing Task Tracker before touching it), as a pair-programmer for the two features, and as a test runner/debugger via its bash tool, which let it actually execute pytest and curl rather than just guess at behavior. I didn't use it to generate the features from a blank prompt — both the search/filter endpoint and the activity log already existed in the starter repo from earlier module work, so my job was closer to a code review: verify the implementation actually matched the acceptance criteria, and fix what didn't.

One moment AI genuinely helped: running the test suite first, before writing anything, turned up two real bugs I would likely have missed by reading the code alone — a duplicate `PATCH /tasks/{task_id}` route where the second (correctly validated) definition was silently dead code, and a missing `GET /tasks/{task_id}` endpoint that the tests expected but the router never defined. Having the AI actually execute the tests and read the tracebacks, rather than eyeballing the code, is what surfaced these; a visual pass over `main.py` alone likely wouldn't have caught that FastAPI resolves duplicate routes by registration order.

One moment it slowed things down: the AI's first instinct was to treat this as a "build two features from scratch" task, which meant it started drafting new endpoint code before I redirected it to read the existing repo first. Once redirected, it correctly recognized the features were already implemented and switched to a verify-and-fix posture. The lesson was to make it inspect the actual codebase before proposing a plan, rather than pattern-matching the assignment brief to a blank-slate build.

One place where my review changed the result: the AI's default fix for the duplicate-route bug was to just delete the second definition and keep the first (unvalidated) one, since it appeared first in the file and "worked" in the sense that it returned 200s. I rejected that — the whole point of `business_rules.py`'s `validate_status_transition` is to enforce the state machine, and silently accepting invalid transitions defeats it. I had it keep the validated version and delete the dead one instead, then reran the transition tests to confirm `422` came back correctly. That's a case where "the tests pass" wasn't sufficient on its own — I had to check *which* code path was actually running.
